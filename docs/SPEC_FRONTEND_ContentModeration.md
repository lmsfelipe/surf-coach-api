# SPEC — Content Moderation: Frontend Implementation

> **Feature:** Server-side content moderation for media uploads
> **Last updated:** 2026-06-08
> **Companion doc:** `FRONTEND_INTEGRATION.md` (Media section)
> **Stack:** React + TypeScript + TanStack Query + shadcn/ui + react-hook-form

---

## 1. What Changed on the Backend

Every media upload now passes through a Gemini Vision moderation step **before** the file is stored. Two new rejection reasons can come back from `POST /api/v1/sessions/{session_id}/media/`:

| Code | HTTP | Meaning |
|---|---|---|
| `MEDIA_NOT_SURF_RELATED` | 422 | Content doesn't show surfing or water sports |
| `EXPLICIT_CONTENT` | 422 | Content contains explicit, adult, or offensive material |

Both use the same error envelope shape the API already uses for every other error:

```json
{
  "error": {
    "code": "MEDIA_NOT_SURF_RELATED",
    "message": "Uploaded media does not appear to be surf or water sports related.",
    "details": {
      "reason": "Shows a soccer game."
    }
  }
}
```

```json
{
  "error": {
    "code": "EXPLICIT_CONTENT",
    "message": "Uploaded media contains explicit or offensive content.",
    "details": {
      "reason": "Contains nudity."
    }
  }
}
```

> **`details.reason`** is a one-sentence English explanation generated by the AI. Do **not** surface it in the UI — use hardcoded Portuguese copy instead. You may log it for debugging.

---

## 2. When Moderation Fires

Moderation runs **per file**, sequentially, during the batch upload. The first file that fails causes the entire request to return a 422. Files processed before the failure are **not** stored.

This means the frontend does **not** need to handle partial-upload state — the response is always all-or-nothing: either `201` with all media objects, or a `422` with a single error object.

## 4. Upload Mutation — Updated Error Handling

If you have an existing `useUploadMedia` mutation, add handling for the two new codes. The error shape hasn't changed — just two new `code` values to recognize.

```ts
// src/hooks/useUploadMedia.ts

import { useMutation, useQueryClient } from "@tanstack/react-query";
import { apiClient } from "@/lib/apiClient";
import { getMediaUploadErrorMessage } from "@/lib/errors";

interface UploadMediaParams {
  sessionId: string;
  files: File[];
}

export function useUploadMedia() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async ({ sessionId, files }: UploadMediaParams) => {
      const form = new FormData();
      files.forEach((file) => form.append("file", file));

      const res = await apiClient.post(
        `/api/v1/sessions/${sessionId}/media/`,
        form,
      );
      return res; // MediaOut[]
    },
    onSuccess: (_, { sessionId }) => {
      queryClient.invalidateQueries({ queryKey: ["media", sessionId] });
    },
    onError: (error) => {
      // error.code is one of the known codes — handled in the UI layer (see §5)
    },
  });
}
```

The `apiClient` should already parse the `{ error: { code, message, details } }` envelope and throw with `error.code` accessible. If it doesn't, align it with the pattern below:

```ts
// src/lib/apiClient.ts — ensure this shape is thrown on non-2xx

export class ApiError extends Error {
  constructor(
    public code: string,
    message: string,
    public details?: Record<string, unknown>,
  ) {
    super(message);
  }
}

async function handleResponse(res: Response) {
  if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    const err = body?.error ?? {};
    throw new ApiError(
      err.code ?? "UNKNOWN_ERROR",
      err.message ?? "Erro inesperado.",
      err.details,
    );
  }
  return res.json();
}
```

## 5. UI Behaviour

### 5.1 Error Display

Show the human-readable message as a **toast** or **inline alert** on the upload form. The message must be in **pt-BR** (use the map from §3).

The two new errors warrant slightly different UX treatment:

| Code | Severity | Suggested UI |
|---|---|---|
| `MEDIA_NOT_SURF_RELATED` | Warning (amber) | Inline alert below file picker with message + option to choose a different file |
| `EXPLICIT_CONTENT` | Destructive (red) | Inline alert or toast — no retry hint |

**Example component:**

```tsx
// src/components/MediaUploadForm.tsx (relevant error section)

import { Alert, AlertDescription } from "@/components/ui/alert";
import { AlertTriangle, XCircle } from "lucide-react";
import { getMediaUploadErrorMessage } from "@/lib/errors";
import type { ApiError } from "@/lib/apiClient";

interface UploadErrorAlertProps {
  error: ApiError;
}

export function UploadErrorAlert({ error }: UploadErrorAlertProps) {
  const message = getMediaUploadErrorMessage(error.code);
  const isExplicit = error.code === "EXPLICIT_CONTENT";

  return (
    <Alert variant={isExplicit ? "destructive" : "default"} className="mt-3">
      {isExplicit ? (
        <XCircle className="h-4 w-4" />
      ) : (
        <AlertTriangle className="h-4 w-4" />
      )}
      <AlertDescription>{message}</AlertDescription>
    </Alert>
  );
}
```

Usage in the upload form:

```tsx
const { mutate: uploadMedia, error, isPending } = useUploadMedia();

// ...

{error && <UploadErrorAlert error={error as ApiError} />}
```

### 5.2 Loading State During Upload

Moderation adds a server-side Gemini Vision call per file — expect **1–3 s of additional latency** compared to a pure file-size/MIME check. Your loading indicator should already cover this, but make sure the upload button stays disabled and a spinner/progress indicator remains visible for the full duration.

Do **not** add a client-side timeout shorter than 30 s for the upload mutation.

### 5.3 File Preview — No Pre-filtering Needed

The frontend does **not** need to attempt client-side surf content detection. The server is authoritative. Keep the existing preview (thumbnail on select) behaviour unchanged.

### 5.4 Re-upload After Rejection

On `MEDIA_NOT_SURF_RELATED`, allow the user to deselect the rejected file(s) and choose new ones without navigating away. Reset the mutation error state when the file selection changes:

```tsx
const [files, setFiles] = useState<File[]>([]);
const { mutate, error, reset } = useUploadMedia();

function handleFileChange(newFiles: File[]) {
  setFiles(newFiles);
  reset(); // clear any previous mutation error
}
```

On `EXPLICIT_CONTENT`, you may choose to clear the entire selection as well — there's no expectation of retrying the same file.
